# Cursor Workflow Boilerplate

Стартовый boilerplate для проектов, которые ведутся через Cursor с агентным workflow. Содержит набор субагентов, навыков (skills), правил (rules) и автоматизацию (hooks) для предсказуемого и качественного процесса разработки.

## Зачем нужен этот репозиторий

- Фиксирует полную историю изменений в правилах, командах и skill-матрице.
- Дает безопасные точки отката, если эксперимент с настройками оказался неудачным.
- Упрощает совместную работу: изменения можно обсуждать через ветки, PR и code review.
- Позволяет стандартизировать запуск проекта через единый набор команд и правил.

## Структура репозитория

```
.cursor/
├── agents/           # 8 специализированных субагентов
├── commands/         # Проектные slash-команды
├── hooks/            # Скрипты автоматизации после событий агента
├── hooks.json        # Конфигурация хуков
├── rules/            # Правила поведения агента (всегда активные и условные)
└── skills/           # Навыки и матрица их применения
.agents/skills/       # Установленные проектные skills
docs/superpowers/     # Шаблоны спецификаций и итерационных планов
```

## Субагенты

Субагенты — специализированные AI-ассистенты, которым Cursor делегирует задачи. Каждый работает в собственном контексте, что изолирует промежуточный вывод и позволяет запускать несколько агентов параллельно.

### Обзор всех субагентов

| Субагент | Модель | Доступ | Связанный Skill | Связанное Rule | Когда использовать |
|---|---|---|---|---|---|
| **planner** | inherit | readonly | `writing-plans` | `00-core-workflow` | Многокомпонентные задачи, дизайн фич |
| **implementer** | inherit | полный | `test-driven-development` | `20-verification-gates`, `30-git-safety` | Выполнение утверждённых планов |
| **verifier** | fast | readonly | `verification-before-completion` | `20-verification-gates` | После реализации, перед коммитом |
| **reviewer** | inherit | readonly | `requesting-code-review`, `receiving-code-review` | — | Перед PR, после реализации |
| **debugger** | inherit | полный | `systematic-debugging` | `10-bugfix-flow` | Баги, падения тестов, ошибки |
| **explorer** | fast | readonly | — | — | Незнакомый код, поиск зависимостей |
| **refactorer** | inherit | полный | `test-driven-development` | `20-verification-gates`, `30-git-safety` | Реструктуризация кода, техдолг |
| **docs-writer** | fast | полный | — | `40-docs-sync` | Обновление документации |

### Когда использовать

- **planner** — задача состоит из 3+ шагов. Декомпозирует на атомарные действия, записывает план в `docs/superpowers/plans/`.
- **implementer** — есть готовый план, нужно написать/изменить код. Работает пошагово, запускает тесты после каждого шага.
- **verifier** — кто-то заявил "готово". Независимо проверяет: файлы существуют, тесты проходят, линтер чист.
- **reviewer** — код написан, нужно ревью перед PR. Проверяет корректность, безопасность, стиль, edge cases.
- **debugger** — что-то сломалось. Находит root cause, предлагает минимальный фикс, добавляет регрессионный тест.
- **explorer** — нужно разобраться в чужом коде. Ищет использования, мапит зависимости, строит архитектурную карту.
- **refactorer** — явный запрос на рефакторинг. Сначала гарантирует тестовое покрытие, потом перестраивает пошагово.
- **docs-writer** — изменилась архитектура или workflow. Обновляет README, API docs, developer guides.

### Как вызывать

Явно через `/имя`:

```
/planner спланируй реализацию авторизации
/implementer выполни план из docs/superpowers/plans/auth-plan.md
/verifier проверь что фича X работает
/reviewer просмотри изменения перед PR
/debugger разберись почему падает тест Y
/explorer покажи все использования UserService
/refactorer вынеси дублирующийся код в утилиту
/docs-writer обнови README после добавления нового workflow
```

Или Cursor делегирует автоматически на основе поля `description` каждого субагента.

### Субагент vs Skill

| Субагент | Skill |
|---|---|
| Нужна изоляция контекста | Однократное действие |
| 3+ шагов | Выполняется за один шаг |
| Параллельное выполнение | Повторяемый быстрый action |
| Независимая верификация | Не нужно отдельное контекстное окно |

## Правила (Rules)

| Правило | Тип | Описание |
|---|---|---|
| `00-core-workflow` | Всегда активно | Основной workflow: план -> реализация -> верификация. Под 3+ шагов — `planner` субагент. |
| `10-bugfix-flow` | Условное | Дисциплина багфикса: воспроизведение -> гипотеза -> фикс -> регрессионный тест. Срабатывает на `bug`, `fix`, `broken`, `error`. |
| `20-verification-gates` | Условное | Верификация после изменения кода: запуск тестов, линтера, тайпчекера. |
| `30-git-safety` | Условное | Безопасность git: scoped коммиты, запрет force push без подтверждения. |
| `40-docs-sync` | Условное | Синхронизация документации при изменениях workflow/architecture. |

## Автоматизация (Hooks)

Хуки автоматически срабатывают после событий агента и предлагают следующие шаги.

| Событие | Хук | Что делает |
|---|---|---|
| `subagentStop` (verifier) | `on-verifier-done.sh` | Если найдены проблемы — предлагает `implementer` для исправления. Если всё чисто — предлагает `reviewer`. |
| `subagentStop` (reviewer) | `on-reviewer-done.sh` | Если одобрено — предлагает `finishing-a-development-branch`. Если есть замечания — предлагает `implementer`. |
| `afterFileEdit` | `on-file-edit.sh` | Если изменён файл в `rules/`, `commands/`, `skills/`, `agents/` — напоминает обновить документацию через `docs-writer`. |

## Потоки работы

### Feature Flow

```
brainstorming skill -> planner subagent -> implementer subagent -> verifier subagent -> reviewer subagent -> finishing-a-development-branch skill
```

### Bugfix Flow

```
debugger subagent -> test-driven-development skill -> реализация -> verifier subagent -> reviewer subagent
```

### Refactoring Flow

```
explorer subagent -> refactorer subagent -> verifier subagent -> docs-writer subagent
```

### Параллельные сценарии

- `verifier` + `reviewer` — запустить одновременно после реализации для ускорения
- `explorer` + `docs-writer` — исследовать код и обновлять документацию параллельно
- `planner` может запустить `explorer` как дочерний агент для сбора контекста

## Быстрый старт

1. Клонировать репозиторий.
2. Запустить `/start-project` для первичной настройки контекста и приоритетов.
3. Работать через профильные команды и субагентов.
4. Перед коммитом — `verifier` проверяет работу, `reviewer` делает ревью.
5. Поддерживать изменения в git через небольшие и понятные коммиты.

## Зачем это нужно команде

- **Быстрый онбординг** — новый участник получает готовую рабочую среду с документированным процессом.
- **Предсказуемый процесс** — plan -> implement -> verify -> review на каждом шаге.
- **Меньше ручной рутины** — автоматические проверки через hooks и verifier.
- **Единый подход** — к документированию, качеству изменений и code review.
- **Изоляция контекста** — субагенты не засоряют основной диалог промежуточным выводом.
